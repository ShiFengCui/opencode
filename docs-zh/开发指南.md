## 一、开发环境设置

### 1.1 系统要求

- **运行时**: Bun 1.3.10+
- **Node.js**: 22+ (兼容模式)
- **包管理器**: Bun (项目使用 `bun.lockb` 锁定文件)
- **操作系统**: Linux / macOS / Windows (WSL2)

### 1.2 安装依赖

```bash
# 克隆仓库
git clone https://github.com/anomalyco/opencode.git
cd opencode

# 安装依赖
bun install

# 设置 Husky hooks
bun run prepare
```

### 1.3 环境变量

创建 `.env` 文件（可选）:

```bash
# 服务器密码（生产环境必需）
OPENCODE_SERVER_PASSWORD=your-password

# 服务器用户名（可选，默认 opencode）
OPENCODE_SERVER_USERNAME=your-username

# AI 提供商 API Key
ANTHROPIC_API_KEY=sk-ant-xxx
OPENAI_API_KEY=sk-xxx
```

## 二、构建命令

### 2.1 根目录命令

```bash
# 开发模式
bun run dev              # 启动 CLI 开发模式
bun run dev:web          # 启动 Web 开发服务器 (Astro)
bun run dev:desktop      # 启动 Tauri 桌面应用开发

# 代码质量
bun run typecheck        # 类型检查所有包 (Turbo)
bun run test             # 运行测试（根目录被禁用）

# 其他
bun run prepare          # 安装 Husky hooks
```

### 2.2 packages/opencode 命令

```bash
cd packages/opencode

# 开发
bun run dev              # 运行 CLI 热重载
bun run build            # 构建生产二进制

# 测试
bun run test             # 运行所有测试
bun run test <pattern>   # 运行匹配模式的测试
                         # 例如：bun run test filesystem

# 代码质量
bun run typecheck        # TypeScript Go 类型检查
bun run lint             # Lint 检查（实际运行测试）
bun run format           # 格式化代码

# 数据库迁移
bun run db generate --name <slug>  # 生成 Drizzle 迁移
```

### 2.3 其他包命令

```bash
# Web UI (packages/web)
cd packages/web
bun run dev        # Astro 开发服务器
bun run build      # 生产构建

# SDK (packages/sdk/js)
cd packages/sdk/js
./script/build.ts  # 重新生成 SDK
```

### 2.4 运行单个测试

测试使用 Bun 测试运行器，从 `packages/opencode` 目录运行：

```bash
cd packages/opencode

# 运行所有测试
bun test

# 运行特定测试文件
bun test test/util/glob.test.ts

# 运行匹配模式的测试
bun test filesystem      # 匹配 "filesystem"
bun test permission      # 匹配 "permission"
bun test session         # 匹配 "session"

# 自定义超时
bun test --timeout 30000
```

**重要**: 测试不能从仓库根目录运行（会触发 guard）。

## 三、代码规范

### 3.1 一般原则

- **简洁优先**: 保持代码简单，避免过度设计
- **函数式风格**: 优先使用纯函数，避免可变状态
- **类型安全**: 使用 TypeScript，避免 `any` 类型
- **Bun API**: 优先使用 Bun 原生 API（如 `Bun.file()`, `Bun.$`）

### 3.2 命名约定

**变量和函数**: 使用单个单词（如果可能）

```typescript
// ✅ Good
const foo = 1
function journal(dir: string) {}

// ❌ Bad
const fooBar = 1
function prepareJournal(dir: string) {}
```

**减少变量数量**: 内联只使用一次的值

```typescript
// ✅ Good
const journal = await Bun.file(path.join(dir, "journal.json")).json()

// ❌ Bad
const journalPath = path.join(dir, "journal.json")
const journal = await Bun.file(journalPath).json()
```

### 3.3 导入约定

- 使用绝对路径：`@/` 表示 `src/`, `@tui/` 表示 `src/cli/cmd/tui/`
- 分组导入：外部包优先，然后内部导入
- CommonJS 模块使用默认导入

```typescript
import { $ } from "bun"
import path from "path"
import z from "zod"
import { NamedError } from "@opencode-ai/util/error"
import { Instance } from "../project/instance"
```

### 3.4 解构约定

避免不必要的解构，使用点标记保持上下文：

```typescript
// ✅ Good
obj.a
obj.b

// ❌ Bad
const { a, b } = obj
```

### 3.5 变量声明

优先使用 `const`，使用三元运算符或提前返回：

```typescript
// ✅ Good
const foo = condition ? 1 : 2

// ❌ Bad
let foo
if (condition) foo = 1
else foo = 2
```

### 3.6 控制流

避免 `else` 语句，优先提前返回：

```typescript
// ✅ Good
function foo() {
  if (condition) return 1
  return 2
}

// ❌ Bad
function foo() {
  if (condition) return 1
  else return 2
}
```

### 3.7 错误处理

使用 `NamedError` 模式：

```typescript
import { NamedError } from "@opencode-ai/util/error"
import z from "zod"

export const MyError = NamedError.create(
  "MyError",
  z.object({
    message: z.string(),
    code: z.number(),
  }),
)

// 抛出
throw new MyError({ message: "Something failed", code: 500 })

// 捕获和处理
if (err instanceof NamedError) {
  return c.json(err.toObject(), { status: 500 })
}
```

**避免 try/catch**: 让错误传播，除非需要特殊处理

### 3.8 数据库 Schema (Drizzle)

使用 snake_case 字段名：

```typescript
// ✅ Good
const table = sqliteTable("session", {
  id: text().primaryKey(),
  project_id: text().notNull(),
  created_at: integer().notNull(),
})

// ❌ Bad
const table = sqliteTable("session", {
  id: text("id").primaryKey(),
  projectID: text("project_id").notNull(),
  createdAt: integer("created_at").notNull(),
})
```

### 3.9 测试规范

- **避免 mocks**: 尽可能测试实际实现
- **不要重复逻辑**: 测试应该验证结果，不是重复实现
- **集成测试优先**: 测试真实代码路径
- **描述性名称**: 使用嵌套 `describe` 块

```typescript
describe("session", () => {
  describe("create", () => {
    test("creates session with title", async () => {
      // ...
    })
  })
})
```

### 3.10 格式化规则

- **分号**: 不使用（Prettier 强制）
- **行宽**: 120 字符
- **引号**: 单引号优先
- **尾随逗号**: 多行对象/数组使用

## 四、测试指南

### 4.1 测试结构

```
packages/opencode/
├── src/              # 源代码
├── test/             # 测试文件
│   ├── util/
│   ├── session/
│   ├── tool/
│   └── ...
└── package.json
```

### 4.2 编写测试

```typescript
import { expect, test, describe } from "bun:test"
import { Session } from "../src/session"

describe("Session", () => {
  describe("create", () => {
    test("creates session with default title", async () => {
      const session = await Session.create({
        directory: "/tmp/test",
      })

      expect(session.title).toBeDefined()
      expect(session.directory).toBe("/tmp/test")
    })

    test("creates session with custom title", async () => {
      const session = await Session.create({
        directory: "/tmp/test",
        title: "My Session",
      })

      expect(session.title).toBe("My Session")
    })
  })
})
```

### 4.3 运行测试

```bash
cd packages/opencode

# 所有测试
bun test

# 特定文件
bun test test/session/session.test.ts

# 匹配模式
bun test session
bun test permission
bun test tool/bash

# 带超时
bun test --timeout 30000
```

### 4.4 测试最佳实践

✅ **推荐**:

- 测试实际行为，不是实现细节
- 使用描述性测试名称
- 保持测试独立（可并行运行）
- 测试边界条件和错误情况

❌ **避免**:

- Mocks（除非绝对必要）
- 测试中重复业务逻辑
- 依赖测试执行顺序
- 从根目录运行测试

## 五、Git 工作流

### 5.1 分支策略

- **默认分支**: `dev`
- **功能分支**: `feature/your-feature`
- **修复分支**: `fix/bug-description`
- **发布分支**: `release/v1.2.0`

### 5.2 提交规范

```bash
# 格式：<type>(<scope>): <description>

# 示例
feat(session): add session compaction feature
fix(permission): resolve timeout issue in ask flow
docs(api): update API documentation
test(tool): add bash tool integration tests
refactor(storage): simplify storage API
```

**类型**:

- `feat`: 新功能
- `fix`: Bug 修复
- `docs`: 文档更新
- `test`: 测试相关
- `refactor`: 代码重构
- `chore`: 构建/工具配置

### 5.3 提交前检查

```bash
# 1. 类型检查
bun run typecheck

# 2. 运行测试
bun test

# 3. 格式化
bun run format

# 4. 提交
git add .
git commit -m "feat: your feature"
```

### 5.4 推送和 PR

```bash
# 推送到远程
git push -u origin your-branch

# 创建 PR（使用 gh CLI）
gh pr create --title "feat: your feature" --body "Description of changes"
```

## 六、贡献流程

### 6.1 提交代码

1. **Fork 仓库** (外部贡献者)
2. **创建分支**: `git checkout -b feature/your-feature`
3. **开发并测试**: 确保测试通过
4. **提交更改**: 遵循提交规范
5. **推送分支**: `git push -u origin feature/your-feature`
6. **创建 PR**: 描述更改内容和测试方法

### 6.2 PR 要求

- **描述清晰**: 说明更改内容和原因
- **测试覆盖**: 添加或更新测试
- **类型检查**: 通过 `bun run typecheck`
- **代码格式**: 通过 `bun run format`
- **文档更新**: 更新相关文档（如适用）

### 6.3 代码审查

- 至少需要 1 个维护者批准
- 解决所有审查意见
- 保持 PR 小而专注
- 及时响应反馈

### 6.4 合并策略

- **Squash and Merge**: 小功能或 Bug 修复
- **Rebase and Merge**: 保持提交历史清晰
- **Merge Commit**: 大型功能分支
